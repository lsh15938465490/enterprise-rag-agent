# 后端知识点学习指南（小白详解版）

> 面向零基础。以本仓库 `enterprise-rag-agent` 为唯一练手项目。  
> 配套文件地图：`需求/前后端代码文件小白解读.md`  
> 路径以仓库根目录为准，例如：`F:\ai\code\text\enterprise-rag-agent`

---

## 这份文档要学什么

下面这些点，本仓库后端**实际用到了**（NestJS 除外）：

| 编号 | 知识点 | 本项目情况 |
|------|--------|------------|
| A | FastAPI 基础接口、POST/GET、流式接口 | 有（无 NestJS） |
| B | RAG 全流程：解析、切片、Embedding、入库、检索 | 有，且是核心 |
| C | Function-Calling：工具注册、参数解析、任务调度 | 有，但是 **ReAct JSON + LangGraph**，不是 OpenAI 原生 `tool_calls` |
| D | 跨域、JWT 鉴权、接口拦截、请求封装 | 跨域/JWT/拦截在后端；请求封装主要在前端 `http.ts` |
| E | 日志、异常捕获、错误统一处理 | 有 |
| F | Docker 打包、compose、服务器基础运维 | 仓库有 Docker；运维是部署时练 |

**重要说明：** 不要先学 NestJS。本项目后端是 **Python + FastAPI**。

## 第 0 步：先把环境跑通（建议 1 天）

### 0.1 目标

搞清楚一件事：

> 浏览器 / Swagger → 发 HTTP 请求 → 进到 FastAPI 某个函数 → 返回 JSON 或流式文字。

还没搞懂「请求进哪个函数」之前，不要急着学 RAG。

### 0.2 你需要提前装好的软件

| 软件 | 用途 | 注意 |
|------|------|------|
| Docker Desktop | 跑 Postgres / Redis / Qdrant | Windows 需 WSL，装完重启；左下角要变成 Running |
| Python 3.11 或 3.12 | 跑后端 | **不要用 3.13** |
| 可选 Node.js | 跑前端页面 | 第 0 步只用 Swagger 也可以 |
| 可选 DeepSeek API Key | 真正生成中文回答 | 不配也能学接口和检索，回答可能是占位句 |

### 0.3 详细操作步骤

#### 步骤 A：复制环境变量

在项目根目录打开 PowerShell：

```powershell
cd F:\ai\code\text\enterprise-rag-agent
Copy-Item .env.example .env
```

用记事本打开 `.env`，先不用改也能跑开发环境。  
若已有 DeepSeek Key，可填：

- `DEEPSEEK_API_KEY=你的key`  
  或  
- `LLM_API_KEY=你的key`

**不要把 `.env` 提交到 Git。**

#### 步骤 B：启动三个中间件

确认 Docker Desktop 已 Running，然后：

```powershell
cd F:\ai\code\text\enterprise-rag-agent
docker compose up -d postgres redis qdrant
docker compose ps
```

期望看到 postgres / redis / qdrant 为 `healthy` 或至少 `running`。

对应端口：

- Postgres：`5432`
- Redis：`6379`
- Qdrant：`6333`

若起不来：看 Docker 是否缺镜像源、端口是否被占用。

#### 步骤 C：安装后端依赖并建表

新开一个终端：

```powershell
cd F:\ai\code\text\enterprise-rag-agent\backend
uv sync
```

没有 `uv` 时：

```powershell
cd F:\ai\code\text\enterprise-rag-agent\backend
python -m pip install -e .
```

建表（Postgres 必须已经起来）：

```powershell
cd F:\ai\code\text\enterprise-rag-agent\backend
uv run alembic upgrade head
```

或：

```powershell
python -m alembic upgrade head
```

#### 步骤 D：启动后端

```powershell
cd F:\ai\code\text\enterprise-rag-agent\backend
uv run uvicorn app.main:app --reload --port 8000
```

或：

```powershell
python -m uvicorn app.main:app --reload --port 8000
```

终端出现类似 `Uvicorn running on http://127.0.0.1:8000` 即成功。  
**这个窗口不要关**，关了接口就停了。

#### 步骤 E：用浏览器验证

1. 打开健康检查：  
   [http://localhost:8000/api/v1/health](http://localhost:8000/api/v1/health)  
   期望 `postgres` / `redis` / `qdrant` 基本为可用状态。

2. 打开 Swagger 文档：  
   [http://localhost:8000/docs](http://localhost:8000/docs)

3. 在 Swagger 里找 `GET /api/v1/auth/tenants`，点 **Try it out → Execute**。  
   应返回部门列表（如部门01 `demo` 等）。

4. 找 `POST /api/v1/auth/login`，填入开发账号（启动成功后 seed 会写入），例如：

```json
{
  "tenant_slug": "demo",
  "username": "admin01",
  "password": "Admin@123456"
}
```

超级管理员可试（无部门时按接口实际字段填写，常见用户名 `adminliu`，密码同样是 `Admin@123456`）。以 `seed.py` 与登录页提示为准。

5. 登录成功后，响应里会有 `access_token`。复制它。

6. 点击页面右上角 **Authorize**，输入：

```text
Bearer 这里粘贴access_token
```

有的 Swagger 只需填 token 本身，按页面提示来。

7. 再执行 `GET /api/v1/auth/me`。  
   应返回当前用户信息（用户名、角色等）。

| 现象 | 可能原因 |
|------|----------|
| 连不上数据库 | Postgres 没起，或 `.env` 里 `DATABASE_URL` 不对 |

## 第 1 步：FastAPI 基础接口与流式（建议 2～3 天）

### 1.1 要建立的概念（先读懂这 4 句）

1. **路由**：某个 URL + 方法（GET/POST）对应 Python 里的一个函数。  
2. **Depends**：函数参数可以声明「先执行某个依赖」，例如「先解析当前登录用户」。  
3. **Pydantic 模型**：请求体 JSON 的形状校验（缺字段、类型错会 422）。  
4. **SSE 流式**：不是一次性返回整段答案，而是多次推送 `data: ...\n\n`，前端边收边显示。

### 1.2 按顺序读源码（每天读透一个）

#### Day1：请求是怎么挂到应用上的

| 顺序 | 文件 | 你要回答的问题 |
|------|------|----------------|
| 1 | `backend/app/main.py` | `app` 是在哪创建的？`/api/v1` 是怎么挂上去的？ |
| 2 | `backend/app/api/v1/router.py` | `auth`、`chat`、`documents` 分别是哪行 `include_router`？ |
| 3 | `backend/app/api/v1/health.py` | `GET /health` 做了什么检查？ |

**操作建议：**

1. 打开 `main.py`，搜索 `include_router` 或 `api_router`。  
2. 打开 `router.py`，把每个 `include_router(...)` 抄到笔记里，写成表格：「模块 → URL 前缀感觉」。  
3. 浏览器访问 `/api/v1/health`，对照 `health.py` 里每个检查函数。

#### Day2：普通 POST/GET（登录为例）

| 文件 | 关注点 |
|------|--------|
| `backend/app/api/v1/auth.py` | `@router.post("/login")`、`@router.get("/me")` |
| `backend/app/schemas/dto.py` | 搜索 `LoginIn`、`TokenOut`、`UserDTO` |

**操作建议：**

1. 在 `auth.py` 里找到 `login` 函数，从上到下标注释（可用纸笔）：  
   - 入参是什么  
   - 查数据库哪一步  
   - 什么时候失败  
   - 成功时返回什么  
2. 用 Swagger 再登录一次，对照响应字段和 `TokenOut`。

#### Day3：流式接口

| 文件 | 关注点 |
|------|--------|
| `backend/app/api/v1/chat.py` | `StreamingResponse`、`text/event-stream`、`event_stream` |
| `backend/app/api/v1/ai_docs.py` | 同样是 SSE，业务是「AI 写文档」 |
| `backend/app/services/llm_deepseek.py` | `stream_chat` 如何一段段 yield 文字 |

**操作建议：**

1. 在 `chat.py` 全文搜索 `StreamingResponse`。  
2. 找到生成器函数（常见名类似 `event_stream`），看它 `yield` 了哪些事件类型（如 `delta`、`citation`、`tool`）。  
3. 若前端已启动：打开智能问答，发一个问题，用浏览器 F12 → Network，点开 chat 相关请求，观察是否持续有数据进来（而不是一次结束）。

### 1.3 小练习（务必动手）

#### 练习 1-A：加一个 Hello 接口

1. 新建或在现有健康模块附近加路由（推荐新建小文件再挂到 `router.py`，避免改乱核心业务）。  
   最小做法示例思路：

   - 在某个 `APIRouter` 上增加：

   ```python
   @router.get("/hello")
   async def hello():
       return {"code": 0, "message": "ok", "data": {"msg": "hi"}}
   ```

   - 注意：本项目成功响应常用 `ok()` 助手（见 `api/v1/helpers.py`），练习时尽量跟现有风格一致。

2. 若新建了 router，在 `router.py` 里 `include_router`。  
3. 因 `--reload`，保存后自动重载。  
4. 打开 `/docs`，找到新接口并 Execute。  
5. 练完后可以删掉，避免污染主分支（除非你想保留学习痕迹另开分支）。

#### 练习 1-B：写一个假流式接口

目标：每秒推一行，共 5 行，格式类似：

```text
data: {"n":1}\n\n
data: {"n":2}\n\n
...
```

步骤：

1. 参考 `chat.py` 里 `StreamingResponse(..., media_type="text/event-stream")`。  
2. 写一个 `async def fake_stream():`，循环里 `await asyncio.sleep(1)` 再 `yield`。  
3. 用 curl 或浏览器扩展测试（Swagger 对流式支持一般，优先 curl）：

```powershell
curl -N http://localhost:8000/api/v1/你的路径
```

4. 观察终端是否每隔约 1 秒出现一行，而不是等 5 秒一次性出来。

## 第 2 步：跨域、JWT、接口拦截、统一报错（建议 2～3 天）

### 2.1 概念（结合本项目场景）

| 概念 | 人话 | 本项目里 |
|------|------|----------|
| CORS 跨域 | 前端跑在 `5173`，后端在 `8000`，浏览器默认拦截跨域，需要后端声明允许 | `main.py` 的 `CORSMiddleware` |
| JWT | 登录成功后发你一张「临时通行证」字符串 | `core/security.py` 签发；请求头 `Authorization: Bearer ...` |
| 接口拦截 | 没通行证或角色不够，进不了函数体 | `core/deps.py` 的 `get_current_user`、`require_roles` |
| 统一报错 | 业务失败不要直接 500 堆栈甩给用户，而是固定 JSON | `AppError` + `exception_handler` |
| 请求封装 | 前端 axios 自动带 token、统一处理 code | **主要在** `frontend/src/api/http.ts`（后端不负责 axios） |

### 2.2 按顺序读源码

#### Day1：CORS + 统一异常

1. 打开 `backend/app/main.py`  
   - 找到 `CORSMiddleware`  
   - 记录：允许哪些 origin（常来自 `.env` 的 CORS 配置）  
2. 同一文件找到多个 `@app.exception_handler(...)`  
   - `AppError`  
   - 参数校验错误  
   - 未捕获 `Exception`  
3. 打开 `backend/app/core/exceptions.py`  
   - 看 `AppError` 有哪些字段：`code`、`message`、`http_status` 等  
4. 打开 `backend/app/core/logging.py`  
   - 知道日志大概是 JSON 行即可，细节第 5 步再挖  

#### Day2：JWT 签发与校验

1. 打开 `backend/app/core/security.py`  
   - `hash_password` / `verify_password`：密码不存明文  
   - `create_token`：access / refresh 两种  
   - `decode_token`：解析 token  
2. 打开 `backend/app/api/v1/auth.py`  
   - 登录成功哪里调用 `create_token`  
   - `refresh`、`logout` 做什么（logout 常会把 jti 拉黑，可顺带看 `core/redis.py`）  

#### Day3：Depends 拦截

1. 打开 `backend/app/core/deps.py`  
   - 精读 `get_current_user`：  
     - 从哪拿 Bearer  
     - 解码失败怎么办  
     - 用户不存在 / 禁用怎么办  
   - 精读 `require_roles`：角色不匹配如何 `AppError`  
2. 任意打开一个需登录的接口，例如 `api/v1/chat.py` 函数参数里的：

   ```python
   user: User = Depends(get_current_user)
   ```

   理解：不是装饰器魔法，是 FastAPI 依赖注入。

### 2.3 小练习（务必动手）

#### 练习 2-A：体验 401

1. 打开 Swagger，点 **Authorize** 清空凭证（Logout）。  
2. 直接调 `GET /api/v1/auth/me`。  
3. 记录返回的 HTTP 状态码和 JSON 的 `code` / `message`。  
4. 对照 `deps.py` 里哪一行抛出了这个错误。

#### 练习 2-B：临时拿掉鉴权（做完必须改回去）

1. 选一个简单接口，例如某个仅 `get_current_user` 的 GET。  
2. 暂时去掉参数里的 `Depends(get_current_user)`（或改成可选，仅作实验）。  
3. 未登录再调一次，观察是否能进。  
4. **立刻恢复代码**，不要提交这种改动。  

目的：用反证理解「拦截」到底拦在哪。

#### 练习 2-C：主动抛统一业务错误

1. 在某个测试用接口或临时逻辑里写：

   ```python

   ```

2. 调用后看响应是否为统一信封，而不是 HTML 报错页。  
3. 对照 `main.py` 的 `app_error_handler`。

#### 练习 2-D：（可选）看前端请求封装

打开 `frontend/src/api/http.ts`，只看三件事：

1. 请求发出前如何附加 `Authorization`  
2. 响应 `code !== 0` 时如何提示  
3. 401 时如何尝试 refresh  

结论写进笔记：**带 token、统一错误提示，主要是前端封装；后端负责签发与校验。**

## 第 3 步：RAG 全流程（重点，建议 1～2 周）

### 3.1 先建立整条流水线心智模型

把下面背熟（默写得出再读代码）：

```text
上传文件
  → 解析（PDF/Word/文本变成文字块）
  → 切片（长文切成小段 Chunk）
  → Embedding（每段变成向量）
  → 入库（Postgres 存文本块；Qdrant 存向量）
  → 用户提问
  → 检索（向量检索 + 关键词检索 → 融合 → 可选精排）
  → 把「问题 + 检索片段」交给大模型
  → 流式生成回答（并带引用）
```

### 3.2 文件与步骤对照表

| 步骤 | 人话 | 必读文件 |
|------|------|----------|
| 上传入口 | HTTP 收文件、落盘、触发流水线 | `api/v1/documents.py` |
| 类型校验 | 防改后缀伪装 | `services/file_kind.py` |
| 存盘 | 文件写到磁盘 | `services/storage.py` |
| 流水线总控 | 状态机 uploaded→…→ready | `services/document_pipeline.py` |
| 解析 | 文件→文字 | `services/parsers/` |
| 切片 | 文字→多段 chunk | `services/chunker.py` |
| Embedding | 文字→向量 | `services/embeddings.py` |
| 向量库 | 写入/搜索 Qdrant | `services/qdrant_store.py` |
| 检索 | 问题→相关片段 | `services/rag_pipeline.py` |
| 融合 | 两路排名合成 | `services/rrf.py` |
| 精排 | 可选交叉编码器 | `services/rerank.py` |
| 问答入口 | 调检索 + 调 LLM | `api/v1/chat.py` |
| 大模型 | HTTP 调云端或占位 | `services/llm_deepseek.py` |

### 3.3 分日学习计划（详细）

#### 第 3 步 · 第 1～2 天：只跟「上传 → ready」

**操作：**

1. 启动前端（可选但推荐）或全程用 API。  
2. 登录部门账号 `admin01`。  
3. 创建一个知识库。  
4. 准备一个很小的 `test.txt`，内容自己写 3～5 段话（含几个独特关键词，方便验证检索）。  
5. 上传到该知识库。  
6. 观察文档状态变化：`uploaded` → `parsing` → `parsed` → `embedding` → `ready`（失败则是 `failed`）。  

**读代码顺序：**

1. `documents.py`：上传成功后哪里调用 `process_document` 或丢给 Celery。  
2. `document_pipeline.py`：从上到下跟 `process_document`，每到改 `status` 的地方做笔记。  
3. `.env` 里看 `INLINE_DOCUMENT_PIPELINE`：为 true 时多半在 API 进程内直接解析。

**加日志实验（做完可删）：**

在 `document_pipeline.py` 切片完成后、向量化前后加：

```python
logger.info("chunks=%s", len(某个列表))
```

重新上传，看后端终端是否打印。

#### 第 3 步 · 第 3～4 天：解析与切片

1. 精读 `parsers/__init__.py`：`parse_file` 如何按后缀分发。  
2. 精读 `chunker.py`：块大概多长、如何滑动窗口。  
3. 用文档的「解析预览」接口/页面（若有 ingest-preview）看切块数量。  
4. 笔记写下：为什么不能整本小说当一个向量？（提示：太长、检索不准、超模型上下文）

#### 第 3 步 · 第 5～6 天：Embedding 与入库

1. 读 `embeddings.py`：  
   - `EMBEDDING_BACKEND=sentence_transformers` 时走哪

## 第 4 步：工具注册、参数解析、任务调度（建议 3～5 天）

### 4.1 先纠正名称

行业常说 **Function Calling**。  
本项目实现方式是：

```text
大模型被要求只输出 JSON
  → 字段含 action、action_input
  → action 只能是 retrieve / execute / finish
  → execute 时到工具白名单里按 name 调用
  → 观察结果写回，再让模型想下一步
  → 图最多循环若干轮（配置里 AGENT_MAX_ITERATIONS）
```

对应技术：提示词约束 + JSON 解析 + **LangGraph** 状态机。  
以后学 OpenAI 官方 Function Calling 时，做如下对照即可：

| 官方概念 | 本项目对应 |
|----------|------------|
| tools 定义列表 | `TOOL_CATALOG` |
| 模型返回的函数名与参数 | `action` + `action_input` |
| 把工具结果塞回对话 | Graph 里 observation / scratchpad |
| 多轮 tool 调用 | supervisor ⇄ retrieve/execute 循环 |

### 4.2 读码顺序（不要乱）

1. `backend/app/tools/registry.py`  
   - `TOOL_CATALOG` 里有哪些工具  
   - `run_tool` 如何校验名字、如何分发  
2. `backend/app/tools/weather.py`、`kb_stats.py`、`sql_query.py`  
   - 单个工具函数签名、失败时返回什么  
3. `backend/app/services/llm_deepseek.py`  
   - `REACT_SYSTEM` 提示词全文读一遍  
4. `backend/app/services/agent_graph.py`  
   - `supervisor_node`：问模型下一步  
   - `retrieve_node` / `execute_node`  
   - `build_agent_graph`：边怎么连  
5. `backend/app/api/v1/chat.py`  
   - 何时走 RAG，何时走 `run_multi_agent`  
6. `backend/app/api/v1/tools.py`  
   - 前端/调试如何列出工具列表  

### 4.3 小练习

#### 练习 4-A：加一个 echo 假工具

1. 在 `registry.py` 的 `TOOL_CATALOG` 增加一项，例如 name=`echo`，描述写清楚参数。  
2. 在 `run_tool` 的分支里，若 name 是 `echo`，把 `args` 转成字符串返回。  
3. 调 `GET /api/v1/tools` 看列表是否出现。  
4. 前端聊天选 **Agent** 模式，提问引导模型去调 echo（可能不稳定，取决于模型是否听话；可先读日志里的 action JSON）。  
5. 观察 SSE 事件里是否有 `tool` 相关推送（对照 `agent_graph.py` 里 `events.append`）。  

#### 练习 4-B：跟踪一次 Agent 循环
