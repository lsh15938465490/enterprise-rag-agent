# 企业知识库问答平台 — 面试技术阐述

> 用途：面试口述腹稿。结构为 **背景问题 → 技术选型与架构思考 → 部署与效果验证 → 踩过的坑与优化**。  
> 对应仓库：`enterprise-rag-agent`（FastAPI + Vue 3 + PostgreSQL + Qdrant + DeepSeek）。  
> 设计依据：`project-design-doc.md`。

---

## 1. 可以在面试中使用的背景问题

介绍项目时，用下面这些问题把故事立住，也方便面试官追问。

### 1.1 你解决的是什么业务问题，而不是又做了一个 ChatGPT？

企业内部制度、手册、岗位职责散落在 PDF / Word 里。员工问「外贸销售要每日更新哪些台账」时，不能靠模型背通用知识，必须**只根据本公司文档回答，并给出出处**；答不上来要明确说「知识库未覆盖」，不能编条款号。

### 1.2 为什么不是单租户 Demo，而要做成多租户？

真实场景是多个部门 / 公司共用一套系统：部门 01 的人不能搜到部门 02 的合同。还要有平台超级管理员看全局，部门管理员管本部门用户和知识库。这决定了**所有业务表带 `tenant_id`，向量检索也必须带租户 + 知识库过滤**。

### 1.3 RAG 和 Agent 为什么要并存，而不是只做检索问答？

- **制度类问题**：走 RAG（检索 → 引用 → 生成）即可。
- **要调工具的问题**：如查天气、只读 SQL，走 Agent 模式。

Agent 用 LangGraph 循环动作：`retrieve` / `execute` / `finish`。制度题应先检索，避免模型直接 `finish` 瞎编。上限 10 轮，防止工具死循环。

### 1.4 你在项目里的角色和边界？

独立负责从设计文档落地到可演示：后端 FastAPI、前端 Vue 3、混合检索、流式问答、权限与会话隔离。

明确不做（体现产品判断）：SSO / LDAP、多模态 OCR、自建微调、文档字段级权限。面试时主动说 **v1 砍什么**，比堆功能清单更像做过产品。

### 1.5 成功标准怎么定义？

对应设计文档，可当考核口径：

- 单文件 ≤ 50MB，标准 PDF / DOCX 能稳定解析。
- 已有向量时，P95 首次 token 延迟目标 ≤ 3s（不含大模型本身抖动）。
- 有命中必须带 `chunk_id`、文件名、页码 / 标题；无命中必须拒答，禁止编造条款号。

## 2. 技术选型与架构思考

口述时按「候选 → 为什么选 → 为什么不选」说。

### 2.1 整体形态

前后端分离：

| 层 | 选型 |
|----|------|
| 前端 | Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus |
| 后端 | FastAPI（异步）+ SQLAlchemy 2 + Alembic + Pydantic v2 |
| 业务库 | PostgreSQL 16（ACL、JSONB、`tsvector`） |
| 向量库 | Qdrant（payload 过滤、按知识库隔离集合） |
| LLM | OpenAI 兼容接口，默认 DeepSeek `deepseek-chat` |
| Embedding | 默认本地 `BAAI/bge-m3`，维度 1024 |
| Rerank | `BAAI/bge-reranker-v2-m3` |
| 开发中间件 | Docker Compose：Postgres / Redis / Qdrant |

开发时本机跑前后端；接近生产时 Nginx 反代 + SSE 关缓冲。

### 2.2 为什么 PostgreSQL + Qdrant，而不是 pgvector 一把梭？

问答高峰时，向量检索和事务、ACL、会话写入会抢同一套 IO。向量独立出去，业务库专注租户、用户、ACL、全文检索。Qdrant 的 payload 过滤（`tenant_id` + `knowledge_base_id`）适合多租户。不选 Milvus：当前规模运维过重。

### 2.3 为什么混合检索，而不是只上向量？

中文制度里的专有名词、台账名、条款号，纯语义容易漂。流水线：

1. Qdrant 向量召回，`top_k=40`，cosine。
2. PostgreSQL 关键词召回：jieba 写入 `tsvector`，失败再 ILIKE，`top_k=40`。
3. RRF 融合（`k=60`），按 `chunk_id` 去重。
4. Rerank 截取 `top_n=8` 进入 Prompt。
5. 无命中或分数不够：回复「当前知识库未覆盖该问题」，禁止编造。

**分数门槛注意**：语义分大约在 0.05～1 时用 0.2 作门槛；RRF 融合分往往只有 0.01～0.03，**绝不能当成没搜到**。

切块约 800 字、相邻重叠 120 字，避免一句话被切断后两边都搜不全。

### 2.4 Embedding 为什么默认本地 bge-m3？

中英混合文档合适，维度固定 1024。每次打云端 embedding 延迟和费用都不可控。LLM 可通过 `LLM_BASE_URL` / Key 切换厂商，检索层不绑死一家。

### 2.5 鉴权与权限怎么分层？

- JWT：access 约 30 分钟 + refresh 约 7 天；密码 bcrypt。
- 角色：`super_admin`（平台超管）/ `tenant_admin`（部门管理者）/ `member`（普通用户）；设计中还有 `kb_editor`。
- 超级管理员跨租户，登录不强制绑定业务部门。
- 部门管理员只管本部门；可改本部门普通用户角色，**不能改自己的管理者角色**。
- 普通用户问答、看有权限的知识库，不能改库、不能进权限管理写操作。
- 知识库停用优先于 ACL：停用后普通用户不能再检索；问答下拉只列出启用库。

### 2.6 流式为什么用 SSE？

首字延迟体感差很多。Nginx / Vite 代理必须关闭缓冲，否则「流式」会变成等全部生成完再刷出。前端聊天用 `fetch` 读 SSE，不用 axios（对 SSE 不友好）。

### 2.7 登录态为什么用 sessionStorage 而不是 localStorage？

同一浏览器两个标签分别登录超级管理员和管理员时，`localStorage` 会共享覆盖 token：A 标签内存里仍是超管，请求却带着 B 的 token，出现「顶栏超级管理员、上传统计却是管理员数据」。改为按标签页隔离后，两个账号可并排演示、互不串号。新标签需重新登录；「复制标签」会拷贝 `sessionStorage`，属于浏览器行为。

### 2.8 Agent 为什么收成 JSON 动作，而不是只绑 function calling？

兼容网关不一定完整支持 tools。动作收敛为 `retrieve | execute | finish`，JSON 解析失败则默认 `retrieve`，比直接编答案更安全。

## 3. 部署与效果验证

### 3.1 怎么部署

**开发环境**

```text
docker compose up -d postgres redis qdrant
本机：uvicorn :8000  +  Vite :5173（/api 代理到后端）
```

| 服务 | 端口 |
|------|------|
| Nginx（生产入口） | 80 |
| 前端 Vite | 5173 |
| FastAPI | 8000 |
| PostgreSQL | 5432 |
| Qdrant | 6333 |
| Redis | 6379 |

**接近生产**

- Compose 拉起 backend / frontend。
- Nginx `:80` 提供静态页，`/api` 反代后端；`proxy_buffering off`，读超时拉长，保证 SSE。
- 启动执行 `alembic upgrade head`。
- 密钥只放 `.env`；生产必须改 `APP_SECRET_KEY` 和默认数据库密码。

### 3.2 怎么验证「真的能用」

按角色走通，比只堆单元测试更像业务验收：

| 角色 | 验收点 |
|------|--------|
| 超级管理员 | 跨部门知识库 / 文档 / 上传统计；可改各部门管理者角色 |
| 部门管理员 | 只见本部门；可改 user01 / user02 角色；不能改自己 |
| 普通用户 | 选库问答、历史会话；无上传与权限写操作 |

演示路径：

1. 上传岗位职责类文档 → 状态到可检索 → 提问 → 流式答案 + 引用（文件名 / 页码）。
2. 故意问库外问题 → 「当前知识库未覆盖该问题」。
3. 停用某个知识库 → 智能问答下拉不再出现，检索不再命中。
4. Agent 模式能看到工具事件；制度类问题会先 `retrieve`。

接口统一信封：`{ code, message, data, request_id }`，便于对照日志排障。仓库内有功能测试用例与执行记录，可说明按用例回归，而不是只点快乐路径。

### 3.3 量化口径

设计目标：解析成功率、首 token P95。落地侧用上传统计（现存 / 可检索 / 失败 / 今日 / 近 7 天趋势）证明入库链路，用引用条数证明答案不是模型凭空生成。

## 4. 踩过的坑与优化

按「现象 → 根因 → 改法」说。

### 4.1 多标签登录串号

- **现象**：超管页顶栏仍是超级管理员，上传统计变成管理员的文档数。
- **根因**：登录态写在 `localStorage`，标签共享；Pinia 内存用户与请求 token 不是同一份身份。
- **改法**：token / 用户写入当前标签的 `sessionStorage`；HTTP 拦截器、路由守卫、SSE、文档下载统一读取；旧 `localStorage` 迁一次后清除。

### 4.2 问答气泡出现「内部错误」

- **现象**：普通用户 RAG 提问，助手直接显示「内部错误」。
- **根因**：未捕获异常被全局处理成 HTTP 500「内部错误」；RAG 调用了 `retrieve` 却漏了 import，`NameError` 发生在 SSE 之前，前端把 JSON 的 `message` 写进气泡。
- **改法**：补导入；会话未绑定启用知识库时按未覆盖处理；检索失败单独提示，避免一律 500。
- **原则**：对外不露堆栈，对内日志和错误码要能区分「代码写错」和「模型挂了」。

### 4.3 融合分被当成语义分，误报未覆盖

RRF 分数很小。若一律用 0.2 截断，关键词明明命中也会说没覆盖。门槛只对近似余弦 / 交叉编码器、落在 0.05～1 区间的分数生效。

### 4.4 SSE 被代理缓冲，流式变成一次性刷出

Nginx `proxy_buffering off`；Vite 代理补 SSE 相关头；前端自行拆 `event:` / `data:`。这条链路不用 axios。

### 4.5 流式写库把请求 Session 用残

用户消息先 `commit`，引用物化，助手消息用独立 session 写入，避免流尚未结束、请求级 session 已半提交或超时。

### 4.6 停用知识库仍能被问答命中

列表、建会话、检索统一过滤 `is_active`；问答接口 `for_qa=true` 只返回启用库。停用优先于 ACL。

### 4.7 超级管理员不属于任何业务部门

`tenant_id` 为空，独立平台租户。登录列表不出现「超级管理员」部门；超管登录不校验所选部门。历史会话的租户列展示**创建人账号所属部门**，超管会话显示为「超级管理员」，避免被算进某个业务部门。

### 4.8 JWT 刷新与切账号竞态

切换账号时递增 `authEpoch`。进行中的 refresh 返回后若 epoch 已变则丢弃，避免把上一用户的新 token 写进当前标签。

### 4.9 已知后续优化（体现判断力）

- 设计上解析 / 向量化应走 Celery + Redis；开发演示可用进程内流水线，生产文档量大时必须队列化。
- Rerank 模型宜单独服务化，避免和 API 进程抢内存。
- 制度问答黄金评测集尚未产品化，目前靠人工用例和引用抽检。

## 5. 一分钟收口

这是一个面向企业的多租户知识库问答：文档进入 PostgreSQL 与 Qdrant，问答做向量 + 关键词混合检索再 rerank，答案带引用，无命中拒答。RAG 解决制度问答，Agent 解决工具调用。权限按超级管理员 / 部门管理员 / 员工拆开，登录态按浏览器标签隔离。上线演示时处理过多标签串号、漏导入导致的假「内部错误」、RRF 分数误伤，以及 SSE 被代理缓冲等问题。

若被问「和只调大模型 API 有什么区别」，落到：**租户隔离、检索融合、引用约束、流式与会话一致性、角色不能自我降权**——这些不在 Prompt 里，在架构里。
